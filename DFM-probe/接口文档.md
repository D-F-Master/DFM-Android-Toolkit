## 统一规范

### 请求方式

设备端不提供 HTTP 接口。PC 侧作为 TCP 客户端主动连入 `0.0.0.0:21104`，按帧协议发送一帧业务帧；
数据区为 UTF-8 JSON **对象**。组帧与停等 ACK 的参考实现见 `pc/probe_test.py` 的
`pack_frame`（`pc/probe_test.py:65-71`）与 `call`（`pc/probe_test.py:131-166`）。

### 状态码说明

帧数据区信封的 `code`：`200` 成功 / `400` 请求参数错误 / `500` 设备端内部错误。

### 帧数据区请求格式

设备端接收的数据区为 UTF-8 JSON **对象**（不能是数组 / `null` / 基本类型），单帧最多 65535 字节。
不是合法 JSON 对象的帧直接丢弃且不回 ACK。各命令字的请求字段见「三、命令字与参数规范」。

### 帧数据区返回格式

设备端应答数据区采用统一 `{code,message,data}` 信封，
由 `ProbeService.java:341-356` 的 `ok()` / `fail()` 统一生成，所有命令字（含未知命令与超长兜底）不再使用 `ok` 布尔字段：

**成功**:

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

**失败**:

```json
{
  "code": 400,
  "message": "错误信息",
  "data": null
}
```

**字段说明**:

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `code` | int | `200` 成功 / `400` 请求参数错误 / `500` 设备端内部错误 |
| `message` | string | 成功固定 `success`；失败为具体错误原因 |
| `data` | object \| null | 成功为该命令字的业务数据对象；失败固定 `null` |

失败时 `data` 固定为 `null`（`JSONObject.NULL`），不省略、不替换成空对象。

### 帧交互流程

业务帧（`0x00`、`0x01`、`0x02`、`0x03`）校验通过先回 ACK（`0x06`），再回同帧序响应帧；
响应帧命令字 = `请求命令字 | 0x80`，不要求 ACK。未知命令字回 `0xFF CMD_ERROR`。
CRC 错或长度非法的帧直接丢弃且不回 ACK；同一帧序重复帧只回 ACK、不重复执行业务。
长度字段为 2 字节、低字节在前，单帧数据区 **最多 65535 字节**。

以下各项均可由本仓库源码核对。

### 2. 帧结构

`AA 55 | 帧序(1B) | 长度(2B，低字节在前) | 命令字(1B) | 数据区 | CRC16(低字节在前)`

| 字段 | 长度 | 说明 |
| --- | --- | --- |
| 帧头 | 2B | 固定 `AA 55` |
| 帧序 | 1B | 0~255 循环；同帧序重传只回 ACK、不重复执行业务 |
| 长度 | 2B | 低字节在前，等于数据区字节数，`MAX_DATA = 65535` |
| 命令字 | 1B | 见「二、帧命令字总表」 |
| 数据区 | N B | UTF-8 JSON 对象，最多 65535 字节 |
| CRC16 | 2B | Modbus，低字节在前；覆盖 `帧序 + 长度(2B) + 命令字 + 数据区` |

组帧 / CRC / 长度上限见 `ProbeService.java:56`、`ProbeService.java:615-636`、`ProbeService.java:639-652`；
PC 侧对拍实现见 `pc/probe_test.py:52-71`、`pc/probe_test.py:74-128`。
ACK 帧为 `AA 55 <同帧序> 00 00 06 <crc_lo> <crc_hi>`（空数据区，`ProbeService.java:262-270`）。

### 3. PC 侧参考实现 `pc/probe_test.py`

| `0x8E` | CMD_SCRIPT_UNZIP_RESPONSE | 设备→PC | 统一信封 | 由 `0x0E \| 0x80` 得到；通知类，不要求 ACK |
| `0x8F` | CMD_SCRIPT_LIST_RESPONSE | 设备→PC | 统一信封 | 由 `0x0F \| 0x80` 得到；通知类，不要求 ACK |
| `0x90` | CMD_SCRIPT_RUN_RESPONSE | 设备→PC | 统一信封 | 由 `0x10 \| 0x80` 得到；通知类，不要求 ACK |
| `0x91` | CMD_CAM_REPLACE_RESPONSE | 设备→PC | 统一信封 | 由 `0x11 \| 0x80` 得到；通知类，不要求 ACK |
| `0x92` | CMD_CAM_RESTORE_RESPONSE | 设备→PC | 统一信封 | 由 `0x12 \| 0x80` 得到；通知类，不要求 ACK |
| `0xFF` | CMD_ERROR | 设备→PC | 统一信封 `{"code":400,"message":"unknown cmd: 0x..","data":null}` | 仅未知命令字；业务异常仍走 `cmd \| 0x80` 响应帧（信封内 `code:500`）；通知类，不要求 ACK |

> 表中「统一信封」指 `{"code":200,"message":"success","data":{...}}`，失败为
> `{"code":400/500,"message":"...","data":null}`，由 `ProbeService.java` 的
> `ok()` / `fail()` 生成；各命令字的业务数据在 `data` 内，字段见「三」。

> 设备端不再有旧 `0x03`~`0x05`、`0x07` 业务命令字；`0x03` / `0x04` / `0x05` / `0x07` 现为
> 串口会话四命令字，`0x06` 保留为 ACK，也没有关闭 TCP 连接的命令字；
> 连接由 PC 侧主动关闭，设备端 `ServerSocket` 常驻监听。

`ProbeService.java` 的 `handleFrame()` 计算 `unknown` 与 `respCmd = unknown ? CMD_ERROR : (cmd | 0x80)`。
PC 侧 `pc/probe_test.py` 的 `call()` 用 `r_cmd in (cmd | 0x80, CMD_ERROR)` 通用匹配响应帧，
因此 `0x00` ~ `0x05`、`0x07` ~ `0x0D`、`0x0E` ~ `0x12` 的响应帧 `0x80` ~ `0x85`、`0x87` ~ `0x8D`、`0x8E` ~ `0x92`
无需为每对命令字单独写匹配分支。

### 3.4 串口会话 `0x04` / `0x03` / `0x05` / `0x07`

按 `串口助手-反编译说明.md` 的透传逻辑：设备端**不做帧头、长度、校验、粘包/半包重组**，
`read()` 返回多少原样回调多少，发送侧把输入原样写出；Hex/Txt 由页面选择展示。
设备端只保持**一个**服务级会话，所有串口方法 `synchronized` 串行化。

- **实现位置**: `ProbeService.java` 的 `serialOpen()` / `serialRead()` / `serialSend()` /
  `serialClose()` / `shutdownSerialSession()` / `stopSerialLoop()` / `appendSerialBytes()` /
  `buildSttyCommand()` / `hexToBytes()` / `toHex()` / `isValidBaud()`，以及 `SerialSession` /
  `SerialReadTask` / `SerialSendTask` 内部类。
- **依赖**: 需设备已 root 且串口节点可读写；设备端直接 open 节点，不经 `adb shell`。

#### 3.4.1 `0x04 CMD_SERIAL_OPEN` 打开会话

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `serial` | string | 是 | 串口设备节点，如 `/dev/ttyS3`；空、含空白或节点不存在回 `400` |
| `baud` | int | 是 | 13 个支持值：`1200` `2400` `4800` `9600` `19200` `38400` `57600` `115200` `230400` `460800` `921600` `1500000` `3000000`；其余回 `400 baud must be one of: ...` |
| `parity` | string | 否 | `none` / `odd` / `even`，默认 `none`，其余回 `400 parity must be none / odd / even` |
| `dataBits` | int | 否 | `5` / `6` / `7` / `8`，默认 `8`，其余回 `400 dataBits must be 5 / 6 / 7 / 8` |
| `stopBits` | int | 否 | `1` / `2`，默认 `1`，其余回 `400 stopBits must be 1 / 2` |

`stty` 命令由 `buildSttyCommand()` 生成：
`stty -F <serial> <baud> cs<N> [-]parenb [parodd] [-]cstopb raw -echo`
（`parity=none` → `-parenb`、`odd` → `parenb parodd`、`even` → `parenb -parodd`；
`stopBits=2` → `cstopb`，否则 `-cstopb`）。`stty` 非 0 退出回 `500 stty failed (exit N): ...`。

成功后 `RandomAccessFile(serial,"rw")` 打开节点，起后台读线程持续 `read()`（每轮 ≤512B、
无数据 sleep 10ms）写入会话缓冲；重复 OPEN 先关旧会话。返回
`{"serial","baud","parity","dataBits","stopBits","stty"}`。

#### 3.4.2 `0x03 CMD_SERIAL_READ` 取增量

不带参数。从会话读缓冲**取全部增量并清空**，返回：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `hex` | string | 空格分隔大写 hex（如 `"01 02 03"`），无数据为空串 |
| `text` | string | 同一批字节的 UTF-8 解码文本（原样，不做转义或帧解析） |
| `bytes` | int | 本轮取出的字节数 |

缓冲上限 `MAX_SERIAL_BUFFER = 65536`，溢出丢最旧字节。未 OPEN 回
`400 serial session not opened`；读线程已退出回 `400 serial read thread stopped`。
PC 轮询此命令字即实现「打开串口持续读」；**应答顺序** `ACK (0x06)` → `0x83`，两帧同帧序。

#### 3.4.3 `0x05 CMD_SERIAL_SEND` 发送

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `mode` | string | 否 | `text`（默认）/ `hex`，其余回 `400 mode must be text / hex` |
| `payload` | string | 是 | 发送内容；空回 `400 payload is required`；`hex` 模式每 2 字符转 1 字节，奇数位 / 非法字符 / 空串回 `400` |
| `times` | int | 否 | 默认 `1`；`0` 表示持续到手动停止，`0..10000`，越界回 `400 times must be 0..10000 (0 = until stopped)` |
| `interval` | int | 否 | 循环间隔毫秒，默认 `500`，`0..60000`，越界回 `400 interval must be 0..60000ms` |
| `stop` | bool | 否 | `true` 时只停止循环发送（幂等），返回 `{"stopped":bool}` |

`times == 1` 时同步 `raf.write(bytes)`；否则起设备端后台线程按 `interval` 定时写出，
**立即回响应**（不等待循环结束）。参数校验在会话状态检查之前，未 OPEN 时参数错误仍回 `400`
参数信息，参数合法但未 OPEN 回 `400 serial session not opened`。
返回 `{"mode","bytes","times","interval","loop"}`（`loop` 表示是否起后台循环）。

#### 3.4.4 `0x07 CMD_SERIAL_CLOSE` 关闭会话

不带参数。置 `reading=false`、停循环线程并 interrupt、`raf.close()`、清缓冲，返回
`{"closed":bool}`（是否确有会话）。服务 `onDestroy` 也会调用 `shutdownSerialSession()`。
**应答顺序** `ACK (0x06)` → `0x87`。

#### 调用方式

按「一、3」依次发送 `0x04`（带 5 参数）→ 轮询 `0x03`（`{}`）→ `0x05`
（`{"mode":"text","payload":"AT"}`）→ `0x07`（`{}`）；
`pc/probe_test.py` 的 `[6/8]` 段覆盖四命令字共 16 个参数校验用例（未 OPEN 读取/发送、
五个 OPEN 参数、`0x05` 载荷与次数/间隔、`0x07` 与 `stop` 幂等），不打开真机串口。

**以下内容为旧版一次性读取（`duration` / `maxBytes`）的真机历史记录**，新 v2.4 协议设备端
已改为会话式、不再返回 `duration`、不做帧解析；`3.4` 的新语义以上文为准。
业务层若仍需按刷卡模块帧格式切帧，由调用方在 PC 侧自行处理。

**真机实测返回（历史记录）**（设备 `202600298120`，已 root，`/dev/ttyS1` -> `/dev/ttyDC1`，刷卡模块 UART 接 `/dev/ttyS1`、`9600`）：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "hex": "02 09 01 50 7A EE 66 AA 03 02 09 01 50 7A EE 66 AA 03",
    "bytes": 18,
    "duration": 4563
  }
}
```

> 设备未 root 或节点不可读写时，`stty` 配置失败 / `open` 被拒通常回
> `500 serial read failed`（`ProbeService.java:402-413`）。

#### 读取结果的帧格式（业务层，非帧协议）

`data.hex` 是串口原始字节，帧协议层不做解析。所接刷卡模块（依据用户提供的
《电子班牌刷卡二次开发接口.doc》）在 `9600` 下输出固定 9 字节帧：

| 字节 | 值 | 说明 |
| --- | --- | --- |
| 1 | `0x02` | 数据头（固定） |
| 2 | `0x09` | 整帧长度 9 字节（含头尾） |
| 3 | `0x01` / `0x02` | 卡片类型：`0x01` MIFARE 1K、`0x02` EM4100 |
| 4~7 | SN0~SN3 | 4 字节卡号 |
| 8 | BCC | 第 2~7 字节逐字节异或 |
| 9 | `0x03` | 数据结尾（固定） |

- 模块文档示例 `02 09 02 04 2E 53 82 F0 03`：卡类型 `0x02` EM4100、卡号 `04 2E 53 82`、
  BCC = `09 ^ 02 ^ 04 ^ 2E ^ 53 ^ 82 = F0`。
- 真机实测 `02 09 01 50 7A EE 66 AA 03`：卡类型 `0x01` MIFARE 1K、卡号 `50 7A EE 66`、
  BCC = `09 ^ 01 ^ 50 ^ 7A ^ EE ^ 66 = AA`，校验通过。
- 一次刷卡可能输出多帧相同数据（实测 `bytes: 18` = 2 帧），需按 `0x02`...`0x03` 切帧去重。
- 实测出现过短帧 `02 09 01 61 12 C6 AE 03`（`bytes: 8`，缺 BCC `13`），
  属读取窗口内未收满整帧；解析前须按帧头 / 长度 / 帧尾 + BCC 校验，不完整帧丢弃或重读。
- `data.duration` 为设备端实际耗时，实测 `6862` / `4563` 均大于请求 `duration: 2000`
  （原因待查）；是否读到数据以 `bytes` / `hex` 为准，不要用 `duration` 判断。

### 3.5 Shell 命令执行 `CMD_SHELL (0x08)`

**响应命令字**: `0x88`  
**描述**: PC 下发 shell 命令，设备端执行并回传 stdout / stderr / 退出码。  
**实现位置**: `ProbeService.java:417-435`（`execute` 分发）、`ProbeService.java:715-775`（`shellExec`）、`ProbeService.java:777-790`（`drainStream` 截断读取）

#### 请求参数

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `command` | string | 必填，且 `trim()` 后非空 | 要执行的 shell 命令；缺失或空白返回 `400 command is required` |
| `root` | bool | 可选，默认 `false` | `true` 时经 `su 0 sh -c <command>` 以 root 执行（需设备已 root）；`false` 用 `sh -c <command>` 以应用身份执行 |
| `timeout` | int | 可选，默认 `30`，范围 `1..120`（秒） | 超时强杀进程，越界返回 `400 timeout must be 1..120 seconds`；超时未退出时 `exit` 返回 `-1` |

```json
{"command": "ls /sdcard", "root": false, "timeout": 30}
```

#### 返回参数

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.stdout` | string | 标准输出，按字节截断至上限 10000 字节 |
| `data.stderr` | string | 标准错误，按字节截断至上限 10000 字节 |
| `data.exit` | int | 进程退出码；`-1` 表示超时被强杀 |
| `data.truncated` | bool | stdout 或 stderr 是否发生截断 |

**成功响应**:

```json
{
  "code": 200,
  "message": "success",
  "data": {"stdout": "...\n", "stderr": "", "exit": 0, "truncated": false}
}
```

**应答顺序**: `ACK (0x06)` → `CMD_SHELL_RESPONSE (0x88)`，两帧同帧序。

#### 调用方式

`DFM-service` 端 `POST /api/probe/message` 传 `{"deviceId":"...","cmd":8,"data":{...}}`；
前端「探针工具 → Shell 命令执行」卡片。

#### 注意

- 以应用身份执行时受 Android 应用沙箱限制（无 `pm`、`dumpsys` 等特权命令），需要特权命令请勾选 root。
- 本设备 su 不支持 `-c`，root 模式固定用 `su 0 sh -c <command>` 形式，勿改为 `su -c`。
- stdout / stderr 各截断至 10000 字节并置 `truncated: true`；响应 JSON 超过单帧 65535 字节时
  由 `handleFrame` 兜底回 `500 response too large: N`（见「四」）。

### 3.7 摄像头拍照 `CMD_CAMERA (0x0A)`

**响应命令字**: `0x8A`  
**描述**: camera2 API 无预览拍照（JPEG，画质 95），照片存应用外部私有目录并返回路径与尺寸。  
**实现位置**: `ProbeService.java:857-1006`（`takePhoto`）、`ProbeService.java:1008-1030`（`pickCamera`）、`ProbeService.java:1032-1042`（`ensureFilesDir`）；权限声明 `AndroidManifest.xml` 的 `uses-permission android.permission.CAMERA`

#### 前置条件

- `AndroidManifest.xml` 已声明 `CAMERA` 权限；**运行时授权由 PC 端完成**：
  `adb shell pm grant com.dfm.probe android.permission.CAMERA`（probe 不弹授权框）。
  权限未授予时返回 `500 camera permission not granted (PC: pm grant ...)`。
- `DFM-service` 的 `POST /api/probe/capture`（`kind=photo`）已自动执行 `pm grant` 后再发帧。
- **Android 11 while-in-use 限制**：probe 的前台服务从后台 START 广播拉起，系统不授予
  CAMERA capability，直接 openCamera 会被 CameraService 拒为
  `CAMERA_DISABLED "disabled by policy"`（appops `allow` 也无法绕过，该检查不走 AppOps）。
  解决：PC 端先 `adb shell am start -n com.dfm.probe/.GhostActivity` 拉起透明辅助 Activity
  （不拦截触摸、不抢焦点、覆盖锁屏、停留 15 秒自动 finish），进程短暂回到 TOP 获得
  CAMERA capability 后（建议间隔 ≥1 秒）再发 `0x0A`；超窗后重试会再次被拒。
  旧版 APK 无此 Activity，`am start` 报 `Error: Activity class ... does not exist`，行为同旧版。

#### 请求参数

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `cameraId` | string | 可选 | 指定摄像头 ID（可用 `0x02` 设备详细信息返回的 `cameras` 列表查询）；必须存在，否则 `400 camera not found: <id>`。缺省时默认取后置（`LENS_FACING_BACK`），无后置取第一个；设备无摄像头返回 `500 no camera on device` |

```json
{"cameraId": "0"}
```

#### 返回参数

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.path` | string | JPEG 绝对路径，形如 `/sdcard/Android/data/com.dfm.probe/files/photo_yyyyMMdd_HHmmss.jpg` |
| `data.size` | int | 文件字节数 |
| `data.cameraId` | string | 实际使用的摄像头 ID |
| `data.width` | int | 图片宽（像素，取该摄像头支持的最大 JPEG 分辨率） |
| `data.height` | int | 图片高（像素） |

**成功响应**:

```json
{
  "code": 200,
  "message": "success",
  "data": {"path": "/sdcard/Android/data/com.dfm.probe/files/photo_20261115_163000.jpg", "size": 184320, "cameraId": "0", "width": 1920, "height": 1080}
}
```

**失败响应**（权限未授予）:

```json
{
  "code": 500,
  "message": "camera permission not granted (PC: pm grant com.dfm.probe android.permission.CAMERA)",
  "data": null
}
```

**应答顺序**: `ACK (0x06)` → `CMD_CAMERA_RESPONSE (0x8A)`，两帧同帧序。

#### 超时与并发

- 打开摄像头 5 秒、配置会话 5 秒、等待成像 15 秒，超时分别返回
  `500 camera open timeout` / `500 capture session timeout` / `500 capture timeout`。
- 同一摄像头被其他进程占用时 `openCamera` 报错回 `500 cmd failed: ...`。
- 拍照全程独占摄像头，结束即释放（`session.close` / `device.close` / `reader.close`）。

#### 调用方式

- 摄像头列表：`DFM-service` 端 `POST /api/probe/cameras` 传 `{"deviceId":"..."}`，内部复用 `0x02`
  设备详细信息帧，返回 `data.cameras`（`[{id, facing, resolution}]`）；无摄像头时为空数组。
  前端「探针工具 → 摄像头拍照」先调它，多于一个摄像头时弹窗选择，再把选中的 `cameraId` 传给拍照。
- 拍照：`DFM-service` 端 `POST /api/probe/capture` 传
  `{"deviceId":"...","kind":"photo","cameraId":"0"}`；服务端把照片读成 base64 放进
  `data.response.data.base64`，随后立即 `adb shell rm -f <path>` **删除设备端照片**
  （`deleted` 为删除结果；读图失败仍删除，并以 `readError` 说明原因）。
  前端直接用该 base64 预览，不再调 `/api/device/files/base64`。
- 截图：`kind=screenshot` 行为不变，响应只带 `data.response.data.path`，由前端调
  `/api/device/files/base64` 读取预览，设备端截图文件保留。

### 3.8 无障碍设置页跳转 `CMD_ACCESSIBILITY_SETTINGS (0x0B)`

#### 请求参数

### 3.9 无障碍组件树 `CMD_ACCESSIBILITY_TREE (0x0C)`

**响应命令字**: `0x8C`  
**描述**: 返回无障碍服务采集的当前活动窗口组件树（`rootInActiveWindow` 递归序列化），用于 UI 结构分析。  
**实现位置**: `ProbeService.java` 的 `accessibilityTree()` / `serializeNode()`、`DfmAccessibilityService.java`（`sInstance` 静态持有）；配置 `res/xml/accessibility_service_config.xml`（`canRetrieveWindowContent=true`）

#### 前置条件

- 设备端已启用「DFM Probe」无障碍服务。未启用时**保底自动拉起系统无障碍设置页**（同 `0x0B` 行为），
  并返回 `500 accessibility service not enabled (已在设备上打开无障碍设置页，请启用 DFM Probe 后重试)`。
- 设备当前有可采集的活动窗口；无窗口（如锁屏、桌面切换瞬间）返回 `500 no active window for accessibility`。

#### 请求参数

无字段，数据区传空对象 `{}`。

#### 返回参数

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.package` | string | 当前窗口所属应用包名 |
| `data.nodeCount` | int | 实际写入响应的节点数（含上限内的全部节点） |
| `data.truncated` | bool | 节点数达到 150 上限被截断时为 `true`，此时树不完整 |
| `data.root` | object | 根节点，字段见下 |

节点对象字段（递归结构，`children` 为子节点数组）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `class` | string | 节点类名，如 `android.widget.Button` |
| `text` | string | 文本内容，无则空串 |
| `desc` | string | contentDescription，无则空串 |
| `id` | string | viewIdResourceName（如 `com.xxx:id/btn_ok`），无则空串 |
| `bounds` | string | 屏幕坐标 `l,t,r,b` |
| `clickable` / `scrollable` / `enabled` | bool | 交互属性 |
| `children` | array | 子节点数组（被截断丢弃的子树不出现） |

**成功响应**:

```json
{
  "code": 200,
  "message": "success",
  "data": {"package": "com.example.app", "nodeCount": 86, "truncated": false, "root": {"class": "android.widget.FrameLayout", "text": "", "desc": "", "id": "", "bounds": "0,0,1080,2340", "clickable": false, "scrollable": false, "enabled": true, "children": []}}
}
```

**失败响应**（服务未启用，设备端已自动拉起无障碍设置页）:

```json
{
  "code": 500,
  "message": "accessibility service not enabled (已在设备上打开无障碍设置页，请启用 DFM Probe 后重试)",
  "data": null
}
```

**应答顺序**: `ACK (0x06)` → `CMD_ACCESSIBILITY_TREE_RESPONSE (0x8C)`，两帧同帧序。

#### 边界与并发

- 节点数上限 150（`ProbeService.java` 的 `MAX_TREE_NODES`）：达到上限停止展开，超限子树整棵丢弃（不在 `children` 出现），`truncated` 置 `true`——防止深层树把响应撑破单帧 65535 字节上限。
- 响应整帧仍超 65535 时由帧层兜底改写 `500 response too large: N`（见「四」）。
- 采集在命令处理线程内同步执行，遍历期间无障碍事件可能并发更新节点树，`AccessibilityNodeInfo` 读取本身线程安全，极端情况下个别节点可能返回过期 bounds；重新发一帧即可取到最新树。

#### 调用方式

`DFM-service` 端 `POST /api/probe/message` 传 `{"deviceId":"...","cmd":12,"data":{}}`；
前端「探针工具 → 无障碍组件树」按钮，树按层级缩进显示在结果区（包名 / 节点数 / 截断标记头行 + 逐节点文本）。

### 3.10 无障碍点击 `CMD_ACCESSIBILITY_CLICK (0x0D)`

**响应命令字**: `0x8D`  
**描述**: 设备端在无障碍组件树中按条件匹配节点，直接对该节点（或其最近可点击祖先）执行
`AccessibilityNodeInfo.ACTION_CLICK`——真无障碍点击，不走坐标注入，可命中不可见/被遮挡控件；
节点不支持 `ACTION_CLICK`（如纯展示控件，自身与祖先链均不可点击）时，经无障碍服务
`dispatchGesture` 在节点 bounds 中心坐标派发 1ms 点击手势兜底（API 24+，无需 root）。  
**实现位置**: `ProbeService.java` 的 `accessibilityClick()` / `findClickableNode()` / `nodeMatches()`；坐标兜底在 `DfmAccessibilityService.dispatchTap()`

#### 前置条件

- 设备端已启用「DFM Probe」无障碍服务。未启用时**保底自动拉起系统无障碍设置页**（同 `0x0C` 行为），
  并返回 `500 accessibility service not enabled (已在设备上打开无障碍设置页，请启用 DFM Probe 后重试)`。
- 设备当前有可采集的活动窗口；无窗口返回 `500 no active window for accessibility`。

#### 请求参数

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `id` | string | 否 | viewIdResourceName **精确相等**，如 `com.xxx:id/btn_ok` |
| `text` | string | 否 | 节点文本 **包含匹配** |
| `desc` | string | 否 | contentDescription **包含匹配** |

至少填一项；多项同时填写时为 AND 关系（全部满足才命中）。每项最长 200 字符。

#### 匹配规则

- 深度优先遍历当前窗口组件树（节点数上限 150，同 `0x0C`），返回首个满足全部已填条件的节点。
- 命中节点自身 `clickable=false` 时，向上回溯取**最近的可点击祖先**执行点击（文本节点常包在父容器按钮内）。
- 自身与祖先链均不可点击时**仍返回该命中节点**：先尝试 `ACTION_CLICK`（预期失败），随后经
  `dispatchGesture` 在节点 bounds 中心派发 1ms 点击手势兜底（API 24+，无需 root）。
- 节点完全不在树中才返回 `404 无障碍树未找到节点（…）`。

#### 返回参数

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.clicked` | bool | 是否完成点击（`ACTION_CLICK` 成功或手势兜底成功均为 `true`；失败直接回错误信封） |
| `data.id` / `data.text` / `data.desc` | string | 原样回显本次匹配条件 |

**成功响应**:

```json
{
  "code": 200,
  "message": "success",
  "data": {"clicked": true, "id": "com.example.app:id/btn_ok", "text": "", "desc": ""}
}
```

**失败响应**（条件未命中 / 手势派发失败 / 服务未启用）:

```json
{"code": 404, "message": "无障碍树未找到节点（id=com.example.app:id/btn_ok）；请确认目标界面在前台", "data": null}
{"code": 500, "message": "节点不支持 ACTION_CLICK 且手势派发失败（clickable=false, dispatchGesture=false）", "data": null}
{"code": 500, "message": "accessibility service not enabled (已在设备上打开无障碍设置页，请启用 DFM Probe 后重试)", "data": null}
```

**应答顺序**: `ACK (0x06)` → `CMD_ACCESSIBILITY_CLICK_RESPONSE (0x8D)`，两帧同帧序。

#### 调用方式

`DFM-service` 端模拟脚本「无障碍点击（accClick）」步骤自动调用（`routes/script.py` 走
`POST /api/probe/message` 传 `cmd:13`）；探针工具页可手工发 `{"deviceId":"...","cmd":13,"data":{"text":"登录"}}` 验证。

### 3.11 设备端离线脚本 `0x0E` / `0x0F` / `0x10`

**描述**: PC 侧把模拟脚本导出 zip（`DFM-service` `export_script_zip` 的产物，布局
`script.json + apk/ + templates/ + signature.txt`）经 `adb push` 送到设备固定地址
`/sdcard/Android/data/com.dfm.probe/files/script_in/`，随后由设备端解压、列出、离线执行，
执行日志逐步骤回传，全程不依赖 PC 在线。  
**实现位置**: `ScriptEngine.java`（独立引擎，`unzip()` / `list()` / `run()`）；
`ProbeService.java` 的 `execute()` 三分支仅做薄壳转发。

#### 3.11.1 `0x0E CMD_SCRIPT_UNZIP` 解压脚本包

**前置条件**: zip 已由 PC 侧 `adb push` 到 `files/script_in/{脚本名}.zip`。

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `zip` | string | 是 | zip 文件名（相对 `script_in/`，自动去 `.zip` 后缀）；空回 `400 zip is required`，含 `/`、`\\`、`..` 回 `400 zip 含非法字符` |

**执行逻辑**: 解压前先清空 `script_store/{脚本名}/` 旧目录（重复导入幂等）；逐条目
canonical path 校验防路径穿越（Zip Slip）；解压后缺 `script.json` 回
`500 script.json not found in zip`。

#### 返回参数（`0x8E`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.script` | string | 脚本名（= zip 文件名去扩展名） |
| `data.steps` | int | `script.json` 的 `steps` 数组长度 |
| `data.files` | int | 实际解压出的文件数 |
| `data.path` | string | 解压目标绝对路径 |
| `data.apks` | array\<string\> | `apk/` 子目录文件名列表（无则空） |
| `data.templates` | array\<string\> | `templates/` 子目录文件名列表（无则空） |

#### 3.11.2 `0x0F CMD_SCRIPT_LIST` 列出脚本

不带参数。返回 `script_store/` 下含 `script.json` 的目录：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.scripts[]` | array\<object\> | 已导入脚本列表，无脚本时为空数组 |
| `scripts[].name` | string | 脚本名（目录名） |
| `scripts[].steps` | int | 步骤数；`script.json` 解析失败时为 `0` 并带 `error` 字段 |
| `scripts[].size` | int | `script.json` 字节数 |
| `scripts[].importedAt` | string | 导入时间（目录 mtime，`yyyy-MM-dd HH:mm:ss`） |

#### 3.11.3 `0x10 CMD_SCRIPT_RUN` 执行脚本

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `script` | string | 是 | 脚本名（`script_store/` 下目录名）；不存在回 `400 script not found: <名>（先发 0x0E 解压脚本包）` |
| `repeat` | int | 否 | 重复轮数，默认 `1`，下限钳到 `1`，超过 `1000` 回 `400 repeat must be 1..1000` |

**执行语义**（与 `DFM-service` 服务端脚本引擎对齐）:

- 支持 `tap` / `longpress` / `swipe` / `input` / `installApk` / `deleteFolder` / `startApp` /
  `stopApp` / `uninstallApp` / `keyevent` / `volume` / `reboot` / `tts` / `accClick` /
  `runScript` / `condition`（分支）。
- `waitFor`（模板匹配）**不支持**：设备端无 OpenCV，遇到时该步骤失败，`logs` 中记录
  `设备端不支持模板匹配`。
- `input` 文本限 ASCII：非 ASCII 回该步骤失败（`input text 仅支持 ASCII 字符`）。
- `condition` 支持 `appInstalled` / `shell` / `time` / `accClick` 四种；`template` 条件
  不支持（同 `waitFor` 原因）。分支动作 `goto` / `stop` / `fail` / `runScript`，跳转上限
  100 次、嵌套深度上限 3。
- `tap` / `longpress` / `swipe` 经 root shell `input tap` / `input swipe` 执行（坐标按
  `videoWidth/videoHeight` 与 `wm size` 实测分辨率换算）；`tts` / `accClick` 复用 `0x01` /
  `0x0D` 的设备端实现。
- **无论脚本成败都回 `code:200`**：由 `data.ok` / `data.error` / `data.logs` 表达结果，
  便于 PC 端拿全量逐步骤日志。

#### 返回参数（`0x90`）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `data.script` | string | 脚本名 |
| `data.ok` | bool | 整脚本是否全部成功（任一步骤失败即 `false`） |
| `data.error` | string \| null | 失败原因；成功为 `null` |
| `data.summary.rounds` | int | 实际执行轮数 |
| `data.summary.steps` | int | 脚本步骤总数 |
| `data.summary.ok` | bool | 同 `data.ok` |
| `data.summary.error` | string \| null | 同 `data.error` |
| `data.summary.durationMs` | int | 执行总耗时（毫秒） |
| `data.logs[]` | array\<object\> | 逐步骤日志 `{no: 步骤序, type: 步骤类型, ok: 成败, message: 说明}`；单条 `message` 超 200 字符截断 |
| `data.truncated` | bool | 日志条数达 500 上限被截断时为 `true` |

**成功响应**（示意）:

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "script": "登录流程",
    "ok": true,
    "error": null,
    "summary": {"rounds": 1, "steps": 3, "ok": true, "error": null, "durationMs": 5230},
    "logs": [
      {"no": 1, "type": "startApp", "ok": true, "message": "started"},
      {"no": 2, "type": "input", "ok": true, "message": "text entered"},
      {"no": 3, "type": "tap", "ok": true, "message": "tapped 540,1200"}
    ],
    "truncated": false
  }
}
```

**应答顺序**（三命令字相同）: `ACK (0x06)` → `0x8E` / `0x8F` / `0x90`，两帧同帧序。

#### 调用方式

`DFM-service` 端串联端点（`routes/probe.py`）:

- `POST /api/probe/script-import` `{"deviceId":"...","zipPath":"D:\\log\\script_exports\\xxx.zip"}`
  —— `adb push` 到 `files/script_in/` 后发 `0x0E`，解压成功自动删设备端 zip。
- `POST /api/probe/script-list` `{"deviceId":"..."}` —— 发 `0x0F`。
- `POST /api/probe/script-run` `{"deviceId":"...","script":"xxx","repeat":1}` —— 发 `0x10`。

也可经通用端点 `POST /api/probe/message` 传 `cmd:14/15/16` 直发。

#### 注意

- **执行超时**: 脚本执行时长受帧协议响应超时限制（service 端 `RESPONSE_TIMEOUT = 120s`）；
  超长脚本（大 `repeat`、长 `interval`、`time` 条件长轮询）会因响应超时失败，
  请控制单次执行时长。
- **响应大小**: 日志上限 500 条 + 单条 200 字符，通常远小于 65535 字节单帧上限；
  极端超长仍由帧层兜底改写 `500 response too large: N`。
- **root 依赖**: `tap` / `swipe` / `installApk` 等步骤经 root shell 执行，设备未 root 时
  对应步骤失败并在 `logs` 记录原因。

### 3.12 摄像头画面替换 `0x11` / `0x12`

把 PC 上的照片或视频作为假画面替换设备摄像头输出（hook 在系统相机 HAL 层，所有
App 均看到替换画面），部署逻辑对齐 `替换摄像头画面` 仓库已验证的 `camreplace` 流程。

#### 3.12.1 `0x11 CMD_CAM_REPLACE` 替换画面

- 前置：PC 侧先把媒体文件 `adb push` 到设备固定地址 `files/cam_in/{文件名}`
  （service 端点自动完成）；设备已 root（部署走 `su 0 sh -c`）。
- 请求：`{"file":"xxx.jpg","cameraId":"2","mirror":false}`。
  - `file`：仅文件名（不含路径），支持图片 `jpg/jpeg/png` 与视频 `mp4/mov/avi/webm/3gp/mkv`；
  - `cameraId`：`0x02` 相机列表返回的 id，设备端映射 `/dev/video{cameraId}`
    （外部相机 id 即 video 节点号）；节点不存在回 `400` 并附 `ls /dev/video*` 结果；
  - `dev`：显式指定目标节点（如 `/dev/video2`），优先于 `cameraId`；
  - `mirror`：镜像补偿（晨检 App 预览自带水平镜像时置 `true`）。
- 设备端流程：媒体转 640x480 JPEG 帧流（图片 1 帧 / 视频 15fps 最多 600 帧）→
  从 APK assets 解出 `camhook.so` → root 部署（remount /vendor、复制 so、首次安装往
  `/vendor/etc/init/android.hardware.camera.provider@2.4-external-service.rc` 插
  `setenv LD_PRELOAD`、写 `/dev/camhook.conf` 与 `/dev/camhook.stream`）→
  rc 已含 LD_PRELOAD 时 `kill $(pgrep -f external-service)` 重启 provider 生效。
- 应答帧 `0x91`，`data` 为 `{dev,frames,streamSize,mirror,rebootRequired,deployOutput,restartOutput?,status}`；
  `rebootRequired=true` 表示首次安装（rc 写入了 LD_PRELOAD），**必须重启设备后再执行一次
  替换**才能生效。

#### 3.12.2 `0x12 CMD_CAM_RESTORE` 恢复真实画面

- 请求 `{}`；设备端写 `enabled=0` 的 `/dev/camhook.conf` 并重启 camera provider。
- 应答帧 `0x92`，`data` 为 `{conf,output}`。

#### service 端串联端点（`routes/probe.py`）

- `POST /api/probe/cam-replace` `{"deviceId":"...","filePath":"D:\\pic\\a.jpg","cameraId":"2","mirror":false}`
  —— 校验本地文件与扩展名后 `adb push` 到 `files/cam_in/` 再发 `0x11`；
  成功后删除设备端源文件；响应超时放宽为 `CAM_RESPONSE_TIMEOUT = 300s`（视频转码可能超过
  默认 `RESPONSE_TIMEOUT = 120s`）。
- `POST /api/probe/cam-restore` `{"deviceId":"..."}` —— 发 `0x12`。

#### 注意

- **root 依赖**：部署与恢复均经 `su 0 sh -c` 执行，设备未 root 时失败。
- **首次安装**：rc 未含 `LD_PRELOAD` 时必须重启设备（provider 只在启动时读取 `LD_PRELOAD`）。
- **执行超时**：service 端对 `0x11` 使用 300s 响应超时，视频转码（600 帧）+ 部署可能耗时较长。

## 四、边界与注意

- **数据区上限**: 长度字段为 2 字节（低字节在前），单帧最多 65535 字节。
  响应超过 65535 字节时，`ProbeService.java:275-278` 把整帧改写为统一格式的
  `{"code":500,"message":"response too large: N","data":null}`，不截断、不丢帧。
  请求数据区超过 65535 字节时，PC 侧 `pc/probe_test.py:65-68` 的 `pack_frame` 抛 `ValueError` 拒绝组帧；
  设备端 `ProbeService.java:615-618` 的 `sendFrame` 同样拒绝超长帧。
- **非对象数据区**: 数据区不是 JSON 对象（如 `[]`）时，`ProbeService.java:254-261` 丢弃该帧
  且不回 ACK，调用方等待 ACK 超时。
- **重复帧序**: 同一帧序重传只回 ACK、不重复执行业务（`ProbeService.java:262-267`），
  避免 TTS 被念两遍。
- **未知命令**: `0x7E` 等未登记命令走 `0xFF CMD_ERROR`，应答数据区为统一格式的
  `{"code":400,"message":"unknown cmd: 0x7e","data":null}`（`ProbeService.java:271`、`:286-288`）。
- **无关闭连接命令字**: 旧 `CMD_QUIT (0x05)` 已删除，连接由 PC 侧主动关闭，设备端服务常驻。
- **TTS 依赖**: 朗读成功需设备已安装可用的系统 TTS 引擎；无真机时此项未做端到端验证。
- **设备详细信息依赖**: `0x02` 的串口 / 摄像头 / 外设列表与 `sn` 依赖真机系统是否允许读取
  `/dev`、`CameraManager`、`InputManager` / `UsbManager`；不可读时降级为空数组或 `Unknown`，
  无真机时列表内容未做端到端验证，且可能与 PC 侧 `adb shell` 采集口径不同。
- **串口会话依赖**: `0x04` / `0x03` / `0x05` / `0x07` 要求设备已 root 且串口节点（如 `/dev/ttyS1`）可读写；
  `stty` 配置失败或 `open` 被拒通常回 `500 serial cmd failed`。Android 设备 `stty` 是否支持
  `csN` / `parenb` / `parodd` / `cstopb` 选项、`RandomAccessFile.read` 阻塞时 `0x07` 的关闭行为
  均未真机验证；旧版一次性读取的真机刷卡数据见 `3.4` 末尾历史记录。
  模块若走 WG 输出模式（CST 引脚选择 W26/W34）则 UART TXD 无数据，读串口恒为空。
- **Shell 依赖**: `0x08` 以应用身份执行时受 Android 沙箱限制，`pm` / `dumpsys` 等特权命令需
  `root: true`；设备未 root 时 `su 0 sh -c` 执行失败回非零 exit 或空输出（不视为探针错误）。
- **截图依赖**: `0x09` 应用身份 `screencap` 在部分 ROM 上被静默拒绝（输出 0 字节），
  已实现自动回退 `su 0 screencap -p`；设备未 root 且直连被拒时回 `500 screencap failed (direct and su)`。
- **拍照依赖**: `0x0A` 需先由 PC 端 `pm grant com.dfm.probe android.permission.CAMERA` 授予运行时权限
  （`DFM-service` 的 `/api/probe/capture` 已自动执行）；摄像头被占用或无摄像头分别回
  `500 cmd failed` / `500 no camera on device`。
- **无障碍依赖**: `0x0C` / `0x0D` 需在设备「设置 → 无障碍」里手动启用「DFM Probe」服务（无法静默授予），
  未启用回 `500 accessibility service not enabled`（并自动拉起设置页）；部分 ROM 对无障碍进程有额外限制
  （如被省略号策略杀掉），服务被杀后 `sInstance` 为空，同样回该错误；组件树截断见 `3.9`；
  `0x0D` 匹配与点击规则见 `3.10`。
- **版本来源**: `data.version` 来自 `DFM-probe/AndroidManifest.xml` 的
  `android:versionName`（当前 `1.0`），升级版本时改此处即可，代码无需改动。
- **部署要求**: 本版命令字为破坏性变更，新 `DFMProbe.apk` 必须与新
  `DFM-service/routes/probe.py`、`DFM-probe/pc/probe_test.py`、`DFM-frontend` 一起使用，
  旧版三端不兼容。
- **离线脚本依赖**: `0x0E` / `0x0F` / `0x10` 需新版 APK（含 `ScriptEngine.java`）；
  `tap` / `swipe` / `installApk` 等步骤需设备已 root（root shell `input` / `pm` 执行）；
  `tts` / `accClick` 步骤复用 `0x01` / `0x0D`（后者需无障碍服务已启用）；
  `waitFor` / `condition.template` 设备端不支持（无 OpenCV），遇到时该步骤失败。
  三命令字**未真机端到端验证**（编译与静态校验通过，见「五」）。
