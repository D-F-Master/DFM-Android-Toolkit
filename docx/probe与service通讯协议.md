**帧头**

帧头固定为 `0xAA 0x55`，占用 2 字节。接收端通过连续匹配这两个字节来判断一帧的起始位置。使用 2 字节帧头可以降低与数据区内容冲突的概率。



**帧序**

帧序字段占用1字节，表示帧序号。例如`0x00`表示是第一个包



**长度字段**

长度字段占用 2 字节，**低字节在前、高字节在后**，表示数据区的字节数。例如长度为 `0x0004`，传输为 `04 00`，表示后面紧跟 4 字节有效数据。

长度字段不包含帧头、长度字段本身、命令字和 CRC。



**命令字**

命令字占用 1 字节，用于区分不同指令或业务类型。例如：

| 命令字 | 名称 | 方向 | 数据区 | 说明 |
| ------ | ---- | ---- | ------ | ---- |

| `0x01` | CMD_TTS | PC → 设备 | `{"text":"..."}` | 调用系统 TTS 朗读，成功返回 `{"status":"done"}` |
| `0x02` | CMD_DEVICE_INFO | PC → 设备 | `{}` | 设备详细信息（基础信息 + 串口 / 摄像头 / 外设列表），见 `DFM-probe_接口文档.md` |

> 旧版 `0x01`~`0x05`、`0x07` 业务命令字已全部删除，本版为破坏性不兼容变更；
> 设备端不再有关闭连接的命令字，连接由 PC 侧主动关闭，服务常驻监听。
> `0x02` / `0x82` 为新增的设备详细信息命令字/响应字。
> `0x03` / `0x83`、`0x04` / `0x84`、`0x05` / `0x85`、`0x07` / `0x87` 为串口会话命令字/响应字：
> 设备端打开串口后持续读并缓冲，`0x03` 取增量，不做帧解析，Hex/Txt 原样显示。
> `0x08` / `0x88`、`0x09` / `0x89`、`0x0A` / `0x8A`、`0x0B` / `0x8B`、`0x0C` / `0x8C`、`0x0D` / `0x8D` 为
> shell 执行 / 屏幕截图 / 摄像头拍照 / 无障碍设置页跳转 / 无障碍组件树 / 无障碍点击命令字/响应字。
> （设备已 root；首次安装需重启设备，见 `DFM-probe_接口文档.md`「3.12」）。



**数据区编码**

数据区为 UTF-8 编码的 JSON 对象（不能是数组或裸值），例如 `{}`、`{"text":"设备语音测试"}`。

长度字段为 2 字节，因此**单帧数据区最多 65535 字节**。发送端在组帧前必须先按 UTF-8 字节数检查，超长直接判失败、不得截断发送。JSON 内不得出现裸换行（换行须写成转义形式），因为本协议不依赖换行分帧。

业务结果 JSON 统一采用对齐 service 的 `{code, message, data}` 信封：成功 `code:200` / `message:"success"` / `data` 为业务对象；失败 `code:400`（请求参数错误）或 `code:500`（设备内部错误）/ `message` 为原因 / `data` 固定 `null`。不再使用 `ok` 布尔字段。示例：

- `{"code":200,"message":"success","data":{"version":"1.0"}}`
- `{"code":200,"message":"success","data":{"status":"done"}}`
- `{"code":200,"message":"success","data":{"androidVersion":"11","serialPorts":[],"cameras":[],"peripherals":[]}}`
- `{"code":400,"message":"empty text","data":null}`
- `{"code":400,"message":"unknown cmd: 0x7e","data":null}`



**CRC**

CRC 采用 CRC16

CRC 覆盖范围包括：帧序 + 长度字段 + 命令字 + 数据区

CRC 结果占 2 字节，**低字节在前、高字节在后**（Modbus/RTU 惯例）。即 `crc & 0xFF` 先发，`crc >> 8` 后发。例如 CRC 计算结果为 `0x1234`，帧尾两字节是 `34 12`。两端必须一致，否则校验永远失败。

CRC16 算法示例

```c
uint16_t crc16_modbus(const uint8_t *data, size_t length)
{
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < length; i++) {
        crc ^= (uint16_t)data[i];
        for (int j = 0; j < 8; j++) {
            if (crc & 0x0001) {
                crc = (crc >> 1) ^ 0xA001;
            } else {
                crc >>= 1;
            }
        }
    }
    return crc;
}
```



**ACK 确认**

需要可靠投递的业务帧，接收端校验通过后必须回 ACK。ACK 使用同一套帧格式，命令字为 `0x06`（ACK）。

| 字段   | 值                         |
| ------ | -------------------------- |
| 帧头   | `AA 55`                    |
| 帧序   | 与被确认业务帧相同         |
| 长度   | `00 00`（低字节在前，无数据区） |
| 命令字 | `0x06`                     |
| CRC    | 覆盖：帧序 + 长度(2B) + 命令字 |

ACK 示例（确认帧序 `0x09` 的业务帧）：

`AA 55 09 00 00 06 83 BA`

规则：

- 仅对 CRC 正确、帧结构完整的业务帧回 ACK。
- ACK 本身不再要求对端回 ACK，避免确认环。
- 同一帧序的重复业务帧（重试）只处理一次业务，但仍回 ACK（幂等）。
- 不需要可靠投递的通知类命令可不要求 ACK；发送端在命令字约定中标明。



**数据响应帧**

对需要返回业务结果的命令，接收端处理流程为：**先回 ACK，再发一条数据响应帧**。

| 字段   | 值                                     |
| ------ | -------------------------------------- |
| 帧头   | `AA 55`                                |
| 帧序   | 与被确认业务帧相同                     |
| 长度   | 数据区字节数（2 字节，低字节在前）       |
| 命令字 | 请求命令字按位或 `0x80`（`0x00` → `0x80`，`0x01` → `0x81`，`0x02` → `0x82`，`0x03` → `0x83`） |
| 数据区 | UTF-8 JSON 业务结果，见「数据区编码」   |
| CRC    | 覆盖：帧序 + 长度(2B) + 命令字 + 数据区 |

数据响应帧属于通知类，**不要求 ACK**；发送端收到 ACK 后即进入等待同帧序响应帧的阶段。未知命令或业务异常时用命令字 `0xFF` 回 `{"code":400,"message":"...","data":null}`，同样不要求 ACK。

一次完整交互示例（CMD_HEARTBEAT，帧序 `0x09`）：

```
PC  → AA 55 09 02 00 00 7B 7D 9B 93
设备 → AA 55 09 00 00 06 83 BA
设备 → AA 55 09 39 00 80 <57 字节：{"code":200,"message":"success","data":{"version":"1.0"}}> 67 72
```



**帧序去重实现约定**

接收端用 `lastSeq` 缓存最近一次**已成功处理业务**的帧序：

- 收到 CRC 正确且结构完整的业务帧，若 `seq == lastSeq`：判定为重传，**只回 ACK，不重复执行业务**（尤其不能重复触发 TTS 朗读）。
- 否则执行业务，业务完成后把 `lastSeq` 更新为该 `seq`，再回 ACK 与响应帧。
- 帧序按 0~255 循环递增；链路空闲超时或对端复位时，双方清空待确认队列并从约定起始帧序重新开始。
- 设备端服务常驻、每连接独立工作线程，但同一连接内串行处理（窗口大小 = 1），保证 `lastSeq` 无并发竞争。



**重试策略**

发送端对需要 ACK 的帧采用停等（stop-and-wait）+ 超时重传：

| 参数           | 建议值   | 说明                                                 |
| -------------- | -------- | ---------------------------------------------------- |
| 超时时间 T     | 200 ms   | 发出业务帧后等待 ACK 的时间                          |
| 最大重试次数 N | 3        | 不含首次发送，即最多共发 4 次                        |
| 退避           | 固定间隔 | 每次超时后立即重发同一帧（帧序、命令字、数据区不变） |

流程：

1. 发送业务帧，启动超时定时器 T，重试计数 `retry = 0`。
2. 在 T 内收到同帧序 ACK：停止重试，本帧成功。
3. 超时未收到 ACK：`retry += 1`；若 `retry <= N`，重发原帧并重启定时器。
4. `retry > N`：判定失败，向上层报告超时；该帧序不再占用，可分配给后续新帧。

约束：

- 未收到 ACK 前不得发送下一需要确认的业务帧（窗口大小 = 1）。
- 重发必须使用相同帧序，便于对端去重。
- 帧序按 0~255 循环递增；对端应缓存最近一次已成功处理的帧序，用于识别重复。
- CRC 错误或长度非法的帧直接丢弃，不回 ACK，由发送端超时重试。
- 链路空闲超时、对端复位时，双方清空待确认队列并重新从约定起始帧序开始。



**响应帧超时**

ACK 只确认「帧已完整收到」，业务本身可能耗时较长（例如 TTS 需要初始化引擎并等待朗读完成）。因此发送端在收到 ACK 后还要等待同帧序的数据响应帧：

| 参数       | 建议值 | 说明                                   |
| ---------- | ------ | -------------------------------------- |
| 响应帧超时 | 120 s  | 收到 ACK 后等待同帧序响应帧的最长时间 |

超时未收到响应帧：判定本次业务失败，向上层报告；连接可继续复用或由发送端关闭。该时间需覆盖接收端业务最坏耗时（引擎初始化最长 30 s + 朗读最长 60 s），并留出余量。
